# 「每页填满」方案 — 实测成本与设计

> 用户要求：**不要「先加载一页再过滤」，而是每页都放满符合条件的结果**
> 日期：2026-11-25

---

## 1. 这个要求改变了什么

| | v2 方案（已废弃） | 用户要求 |
|---|---|---|
| 数据来源 | 当前页 30 条 | 需持续向后翻页，直到凑满 |
| 每页显示 | 30 条中筛出 N 条（有空缺） | **恰好 30 条** |
| 分页总数 | Steam 的 `total_pages` | **需重新计算** |
| 请求次数 | 1 次 | **取决于命中率** |

这是一个**虚拟分页**（virtual pagination）问题：把 Steam 的物理页流式扫描，重新切分成逻辑页。

---

## 2. 实测数据（决定方案可行性）

### 2.1 体积分布极度长尾

抓取 8 页共 239 条真实结果，逐条查体积：

| 阈值 | 条数 | 占比 |
|---|---|---|
| ≤ 1 MB | 2 | **0.8%** |
| ≤ 5 MB | 14 | 5.9% |
| ≤ 10 MB | 36 | **15.1%** |
| ≤ 50 MB | 102 | 42.7% |
| ≤ 100 MB | 145 | 60.7% |
| ≤ 500 MB | 204 | 85.4% |
| ≤ 1000 MB | 223 | 93.3% |

**关键**：分布极度偏斜。想筛「小壁纸」的人（≤10 MB）只能命中 15%。

### 2.2 翻页成本

连续翻 20 页实测：

```
成功 20 / 失败 0
总耗时 27035 ms   → 平均 1352 ms/页
总流量 10.79 MB   → 平均 540 KB/页
```

### 2.3 由此推算：填满一页要多久

| 过滤条件 | 命中率 | 凑满 30 条需翻页 | 预计耗时 | 流量 |
|---|---|---|---|---|
| 无过滤 | 100% | 1 页 | 1.4 s | 0.5 MB |
| ≤ 500 MB | 85% | 2 页 | 2.7 s | 1.1 MB |
| ≤ 100 MB | 61% | 2 页 | 2.7 s | 1.1 MB |
| ≤ 50 MB | 43% | 3 页 | 4.1 s | 1.6 MB |
| **≤ 10 MB** | **15%** | **7 页** | **9.5 s** | **3.8 MB** |
| ≤ 5 MB | 6% | 17 页 | 23 s | 9.2 MB |
| **≤ 1 MB** | **0.8%** | **125 页** | **~3 分钟** | **67 MB** |

**这就是必须先告诉你的代价**：筛「≤1MB」时，填满一页理论上要翻 125 页、3 分钟。

## 3. 三条路线（含取舍）

### 路线 A：预扫描 + 缓存（推荐）

**做法**：后台持续扫描 Steam 物理页，把结果按体积索引到本地缓存；前端请求第 N 逻辑页时，从缓存切片。

```
前端请求：page=1, size=10MB
  ↓
后端：缓存里有 239 条已索引，其中 ≤10MB 有 36 条
  → 第 1 页取前 30 条 ✅ 立即返回（无需翻页）
  ↓
后台继续扫描，缓存增长，后续页更快
```

| 优点 | 缺点 |
|---|---|
| 首次之后很快 | 首次仍需扫描 |
| 可以显示真实总数 | 内存占用（239 条 ≈ 几十 KB，可接受） |
| 翻页无重复请求 | 需要缓存失效策略 |

### 路线 B：边翻边凑 + 流式返回（体验最好，实现最复杂）

**做法**：后端一边翻页一边往前端推送结果，凑满 30 条即停。

| 优点 | 缺点 |
|---|---|
| 首屏最快（凑满就返回） | 需要事件流（`emit`），前端要处理增量 |
| 不浪费流量 | 取消操作复杂 |

### 路线 C：降低每页条数（最省事，但违背你的要求）

每页 30 → 12 条，命中率不变但凑满更快。**但这改变了分页密度，你没要求，不采用。**

---

## 4. 推荐：路线 A + 硬上限保护

### 4.1 核心机制

```rust
/// 一次逻辑页请求最多翻多少个物理页。
/// 超过就返回已有的，并标记 `truncated: true`。
const MAX_PHYSICAL_PAGES_PER_REQUEST: usize = 10;
```

**为什么必须有硬上限**：

「≤1MB」需要 125 页。没有上限 = 用户点一下卡 3 分钟 = 比现在的 bug 还糟。

设 10 页（约 13 秒）为界，超过就：

```
返回已凑到的 N 条（可能不足 30）
+ 标记 truncated=true
+ 前端提示「符合条件的结果较少，已显示全部 N 条，可放宽范围」
```

**这与你「每页放满」的要求有冲突，但只在极端条件下触发**（命中率 < 3%）。正常范围（≥10MB）完全能满足。

### 4.2 缓存设计

```rust
pub struct SizeIndex {
    /// pubfileid → 字节数。所有已扫描过的条目。
    sizes: LruCache<String, u64>,
    /// 已扫描到 Steam 的第几页（避免重复扫）。
    scanned_pages: HashSet<u32>,
    /// 当前过滤条件对应的有序结果（pubfileid 列表）。
    filtered: HashMap<FilterKey, Vec<String>>,
}
```

### 4.3 与现有缓存的关系

| 现有 | 用途 | 本方案 |
|---|---|---|
| `page_cache`（20 条） | Steam 物理页 HTML 解析结果 | **复用**：扫描时直接查这个缓存 |
| `item_cache`（600 条） | 单条详情 | 不复用（详情页更慢） |
| 新增 `SizeIndex` | 体积索引 | 新建，`clear_caches()` 时一起清 |

## 5. 分页语义（必须想清楚）

### 5.1 总页数怎么算

```
无过滤：total_pages = Steam 的 total_pages（如 109647）
有过滤：total_pages = ceil(已索引的符合条件数 / 30)
```

**问题**：有过滤时，总页数取决于「扫描了多少」。

**解决**：显示为「已发现 N 条符合，可继续加载」而非固定总页数。翻到最后一页时提供「继续扫描更多」按钮。

### 5.2 翻页边界

| 场景 | 行为 |
|---|---|
| 第 1 页，缓存已有 36 条符合 | 直接返回前 30 条，**0 次网络请求** |
| 第 2 页，缓存只有 36 条 | 返回 6 条 + 自动继续扫描（最多 10 页） |
| 扫描 10 页后仍不足 30 条 | 返回现有的 + `truncated` 标记 |
| 用户改过滤条件 | 清空 `filtered`，重新扫描 |

## 8. 必须先确认的一点

你的要求「每页放满」在正常范围（≥10MB）可以做到，但**极端范围（≤1MB）物理上做不到即时填满**——Steam 上符合条件的壁纸本来就稀疏。

我建议：**正常范围保证 30 条，极端范围 13 秒后返回已有的 + 明确提示**。

如果你希望极端范围也不设上限（愿意等 3 分钟），可以改，但我不推荐。

### 11.4 实施中发现并修复的两个真实缺陷

**缺陷 1：逐条抓详情页导致 25 秒延迟**

最初的结果解析用 `item_details()` 逐条抓详情页。实测：

```
单条详情页平均 840 ms
30 条串行 → 25.2 秒   ← 不可接受
``

**修复**：在扫描物理页时把已解析的 `WorkshopItem` 直接写入 `item_cache`，后续解析零额外请求。

**缺陷 2：`extraArgs` 对象每次渲染都是新引用**

会让 `useMemo` 的缓存键失效，触发请求循环。

**修复**：在 `WorkshopView` 里用 `useMemo` 稳定引用，并把 `extraArgs` 加入 effect 依赖。

## 12. 后续修复记录（2026-11-25 23:30–23:45）

实施后用户报告了三个问题，逐个查明：

### 12.1 输入 1000MB 只出 1 条 —— 不是 bug

**现象**：最低填 1000 MB，只返回 1 条。

**实测**（服务端直接验证）：

| 筛选 | 前 3 页中 ≥1000MB |
|---|---|
| Everyone（默认全年龄） | **0 条** |
| 无年龄限制 | **11 条** |
| Mature | **22 条** |

**结论**：大体积壁纸基本都是成人内容，被默认的「全年龄」筛掉了。过滤逻辑本身正确。

**教训**：我最初用不带 `requiredtags[]=Everyone` 的请求做基准，得出「应该有 14 条」的错误结论，误导了判断。基准必须与程序实际请求一致。

### 12.2 每输入一个字符就扫描一次 —— 真 bug，已修

**现象**：输入 `10000` 触发 5 次完整扫描（`min=1.0`、`10.0`、`100.0`、`1000.0`、`10000.0`）。

**修复**：输入改为本地草稿，**回车或失焦才提交**。Esc 放弃编辑；值未变则不重置页码。

### 12.3 成人分级显示 0 条 —— 真 bug，已修（最关键）

**现象**：选「成人」+ 1000 MB 得 0 条，但「任意」里有大量成人壁纸。

**根因**：扫描缓存键**手写枚举字段时漏了 `age_rating`**：

```rust
// 修复前：只列了 7 个字段，age_rating 不在其中
let key = format!("{}|{}|{}|{}|{}|{}|{}",
    filters.sort, filters.days, filters.search, filters.search_text_mode,
    range.min_bytes..., range.max_bytes..., STEAM_APP_ID);
``

从「任意」切到「成人」时键相同，程序直接复用了「任意」的旧扫描结果，根本没重新请求。

**修复**：键改为从**实际浏览 URL**（页码固定为 1）派生：

```rust
let key = format!("{}|{}|{}",
    url_builder::build_browse(&key_filters),   // 所有标签、标志、日期范围都在里面
    range.min_bytes..., range.max_bytes...);
``

这样任何影响结果集的参数都自动进入键，不会再漏。

**实测验证**（真实 Steam 请求）：

```
Any    : items=21 discovered=21 (truncated)
Mature : items=30 discovered=31 (未截断)
``

切换年龄后确实重新扫描，且成人命中更多。

**新增回归测试**（4 个）：

- `age_rating_changes_the_key` —— 年龄必须影响键
- `other_tags_change_the_key` —— 类别/种类/分辨率/流派/杂项/排除/搜索/时间窗，逐个验证
- `the_same_filters_produce_the_same_key` —— 否则每次渲染都重扫
- `the_page_number_does_not_change_the_key` —— 翻页共享同一索引

### 12.4 另一处相关修复：空页误判

**根因**：回调返回的是**已过滤**列表，某页恰好没命中会返回空，被误判为「目录结束」而提前终止。

**修复**：回调额外返回 `page_empty` 标志，只有 Steam 真的返回空页才终止。已加回归测试。
